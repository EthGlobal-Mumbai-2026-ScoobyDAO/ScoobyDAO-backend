## Objective and interpretation

User objective: “get hold of a almost genuine honeypot that has not been certified yet and make it go through our system and the conculsion should match the claim for people to be away from it.”

Operational interpretation: find a fresh Ethereum mainnet or Base token with strong, independently testable indications of a sell trap, without relying on an existing public honeypot verdict. Run the actual Scooby pipeline and determine whether its evidence supports a clear avoid-interacting recommendation. A matching conclusion is a hypothesis to test, not a preset expected model output. Inconclusive or contradicted results remain valid outcomes and expose a detection or admission gap; never rewrite a result to make a demonstration pass.

“Not certified yet” is provisionally **no definitive public honeypot designation found in a named, timestamped set of sources at candidate capture**. There is no universal certification registry. Preserve source-by-source positive/negative/unknown results; a failed lookup is unknown and a blank provider label is not proof of safety or global novelty. The teammate can refine this meaning with the user later without blocking method preparation.

## Evidence and disconfirmation protocol

1. Identify the exact chain, token, pool, router, block number/hash and UTC observation time. Reuse captured bytes and hashes. Never join on ticker.
2. Test the specific sell-trap hypothesis rather than a generic risk score: ordinary-user buy/sell behavior, transfer restrictions and privileged/selective exceptions where source and state permit. Static code clues or a single scanner result are leads until corroborated.
3. Use read-only RPC or an isolated local fork/simulation. Record engine/version, request, state assumptions, trade size/route, balances, allowance, gas, deadline and revert/trace or received amount. Compare buy and sell on coherent state; a failed sell alone does not establish a honeypot. Do not spend funds, broadcast transactions, use a user wallet or register an agent on-chain.
4. Rule out wrong route/router/token, missing approval/balance, insufficient gas, deadline/slippage, ordinary taxes, low liquidity, stale reserves, launch-time controls and simulation/provider limitations. A successful sell is counterevidence whose wallet, size and state scope must be reported. Selective traps may allow privileged wallets or some sizes; neither a few sells nor a privileged success proves universal sellability.
5. Where possible corroborate runtime/source match, transfer-control path, storage/controller state and actual transaction traces. Separate confirmed mechanism, reproduced behavior, provider allegation and interpretation. Date every claim; contracts and external controllers can change.
6. Keep reference-label/selection rationale separate from the investigation prompt as far as practical. Supply the producer evidence and a neutral question, not a demanded “honeypot” answer. Record any unavoidable prior-label exposure. Lock the report digest before comparing the reference verdict.
7. Include a known-sellable control scenario and source-failure/ambiguous scenarios to catch a detector that calls everything malicious. Prefer offline/local fixtures for controls; a small validation panel is not a calibrated accuracy, sensitivity or specificity estimate.
8. Five-pillar depth remains required, but missing short history may leave VAE pending while the mechanism evidence supports a scoped warning. Preserve the original user-owned 50-reconstruction math when run; no new score, sufficiency threshold, formula or probability is authorized here.

BLISS stays a separate inconclusive diagnostic draft unless new independently collected evidence changes its assessment. Never relabel it as confirmed to satisfy this milestone.

## Primary method references checked at dispatch

- [Honeypot.is endpoint documentation](https://docs.honeypot.is/ishoneypot) separates simulation success, simulation errors, honeypot results and holder analysis; some result fields may be absent. Treat these as provider assertions with explicit coverage. Unknown or unavailable output is not a negative finding.
- [Ethereum execution API: eth_call](https://ethereum.github.io/execution-apis/api/methods/eth_call/) defines execution without creating an on-chain transaction. Individual calls do not provide a persisted buy-then-sell sequence; the method owner must specify coherent fork/state simulation or its actual limitations.
- [Foundry Anvil documentation](https://www.getfoundry.sh/anvil/index.html) documents forks pinned to a block. Fork execution is local; the remote source may still need archive access and read requests. Capture exact tool/provider versions, block/state and all assumptions.

These are method references, not evidence about any candidate, endorsements of a scanner, or a new numerical screening policy.
