## Current starting point

Read the backend README, HANDOFF, `architecture.md`, `endpoint-schema-map.md`, `app.py`, `store.py`, `worker.py`, and OpenAPI first. It currently imports and validates a report bundle with the frontend builder, exposes `GET /reports/{id}/{version}`, records local review assertions at `POST /reports/{id}/{version}/review`, and queues a draft render at `POST /reports/{id}/{version}/render`. All identities and review receipts are unauthenticated; approved export is not implemented. Worker jobs are at-least-once with expiring leases and no fencing; do not attach an external publish side effect to that worker unchanged. Report v0.2 and candidate v0.1 are frozen. The reader source is vendored in `vendor/reader/`; avoid machine-specific `SCOOBY_FRONTEND_DIR` paths.

## Boundary and lifecycle proposal

- Draft: a successfully validated immutable report version may be viewed internally before sign-off, prominently marked pending; draft access is not a publication event. Restrict access under the eventual application authorization policy.
- Review target: exact report ID and version plus SHA-256 of original `report.json` bytes and a manifest of each version-bound artifact's path, media type and digest. Bind the *rendered publication package* and full report bytes too; a report digest alone cannot prove HTML/PDF identity if render output changes. Define deterministic manifest serialization and version it; do not confuse it with the existing exact-byte report digest. Any changed report, evidence or artifact creates a new immutable version/manifest and requires fresh review.
- Human review: explicitly record approve / request revision / reject, reason, authorized reviewer identity, event time, exact target digest/manifest and authentication evidence. Approval is not publication; a revision or rejection cannot publish. Existing prototype local `approved` records cannot be upgraded into authenticated approval retroactively.
- Publish: a separate explicit, authorized operation checks the latest accepted approval for the exact immutable target at commit time; missing, stale, unverified, changed or revoked review fails closed. Access to published bytes checks authoritative current status. No automatic publication on proof success or approval.
- Revoke and supersede: explicit authorized events preserve previous versions and audit history; serve a current status/tombstone or disable access per policy. Never silently overwrite history. Define who may revoke or supersede, and what old URLs expose, before public release.
- Idempotency and failure: require scoped idempotency key plus request hash; same key/same request returns prior result, same key/different request is conflict. Use transactional state and an outbox with lease fencing and an idempotent publisher; reconcile uncertain delivery and retries. Recheck review state at delivery and ensure a racing revoke cannot expose stale approved content. If delivery cannot be proven, expose pending/failed rather than published.

## Proposed integration records (not frozen-schema changes)

Keep these as separate service-owned records. Agree names and APIs with backend owner before implementation:

1. `publication_target`: report ID/version, original report SHA-256, artifact manifest version/digest, source validation result, immutable artifact locations and generated-at information.
2. `review_request`: target ID, action/decision intent, nonce/challenge, expiration, policy version and authenticated reviewer principal.
3. `review_receipt`: target digest and manifest digest, decision, reason, reviewer principal, verified proof metadata/reference, time, verification method/version and revocation/supersession linkage. Protect sensitive proof metadata; do not log raw proofs or secrets.
4. `publication_event`: event ID, target ID, operation, actor, timestamp, idempotency key/request hash, outcome and predecessor; append-only audit and explicit current-state projection.

Proposed interfaces, not selected route contracts: `prepare_target(validated_bundle)`, `create_review_challenge(target, decision, principal)`, `verify_and_record_review(challenge, proof, explicit_decision)`, `request_publication(target, principal, idempotency_key)`, `revoke_or_supersede(...)`, `get_current_status(target)`. Bind target state atomically to review and publish operations. Distinguish immutable bytes from current policy status; define authorization for reviewers, publishers and revokers separately. Preserve existing frozen report schema; propose a new version only for genuinely new research fields.

## World ID and AgentKit: design decision still open

[World ID IDKit integration](https://docs.world.org/world-id/idkit/integrate) describes app-side proof requests and backend verification; it is a candidate for a direct human proof flow. The [World ID protocol specification](https://worldcoin.github.io/world-id-protocol/world-id-4-specs/index.html) describes signals, nullifiers and session proofs. A proof of personhood is not the reviewer's organizational authorization and is not itself an explicit approval decision. Map an authenticated application principal to the reviewer allowlist independently, require that principal's explicit decision and bind it to the exact target.

[AgentKit integration](https://docs.world.org/agents/agent-kit/integrate) currently describes a Beta x402 flow for verifying human-backed agents, including AgentBook registration and lookup. It does not by itself establish that an authorized human approved this report. Decide whether agent access is needed at all; if used, it is separate from direct human sign-off and must not auto-approve a report. Current official integration docs describe registration and canonical lookup on World Chain. The [older GitHub README](https://github.com/worldcoin/agentkit/blob/main/README.md) is marked deprecated and states a Base default; do not hardcode either based on this handoff. Recheck current SDK/docs and network configuration at implementation time. Registration entails a transaction; none is authorized or performed here.

Before selecting a live proof integration, establish an app/RP and environment, action scope, credential level, supported SDK and verifier version, allowed origins/domain, server-side secret storage and rotation, authorized reviewer identity/enrollment and recovery, and operational ownership. Decide whether uniqueness or session proof semantics fit repeat approvals; nullifiers are scoped to RP/action, so an action reused indiscriminately can prevent repeat decisions. Bind the user-visible explicit decision to a fresh server-generated challenge, report/version/digest/manifest digest, purpose, reviewer session and expiry using the protocol's actual supported signal semantics. Verify the proof server-side against configured app/action and expected signal; enforce freshness, atomic challenge consumption and replay/nullifier policy, and recheck reviewer authorization at commit. A nullifier is not a named reviewer identity. Decide privacy retention and audit requirements with the team.

Do not invent an API endpoint or claim a verified SDK integration. Without configured credentials or a trusted verifier, production verification must fail closed; use an explicitly injected mock only in tests. Store no biometric data, raw proofs or credentials in source or logs.

## Test and acceptance contract

Test: valid draft readable before sign-off; unauthorized or unverified reviewer and invalid/expired/replayed proof rejected; wrong app/action/signal/decision/report/manifest/nonce rejected; disabled reviewer rejected at commit; revision/reject cannot publish; changing one artifact or report byte requires a fresh review; proof success alone never publishes; explicit authorized publish succeeds once; conflicting idempotency key fails; retries and crash after side effect reconcile without duplicates; concurrent publish/revoke and stale leases cannot expose a revoked version; unavailable verifier/publisher fails closed; revoke and supersede retain immutable audit history. Include real integration tests against the selected supported verifier only after credentials and a non-production test environment are authorized; document test limits and avoid live claims based on mocks.
