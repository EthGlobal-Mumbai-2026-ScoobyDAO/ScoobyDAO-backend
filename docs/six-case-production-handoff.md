# Handoff: six case–report pairs and production integration

Status: charter and handoff, 7 November 2026. Owner: receiving engineering teammate. This document does not authorize a release or imply that a report, token, or human decision has been approved.

## Goal and product flow

Deliver the existing bounded research as a readable, graphical case-to-report journey in the deployed application, resembling the reviewed local six-pair preview. **This milestone is display-only: do not run or enable live scouting, investigation, VAE training or LLM calls in production.** Seed precomputed case snapshots, report bundles and charts; retain historical/unreviewed labeling and the existing publication boundary. The preview's explanation and visual presentation must work for remote users. Cases are not live scouts merely because they appear on a case board.

Future agent workflow, outside this milestone: independently policy-qualified cases may proceed automatically; other cases require admin human verification before investigation. A second, separate admin World ID confirmation applies to report sign-off. Consumer pages must not operate either checkpoint. Local diagnostic associations are not approvals.

The initial market scope is Ethereum mainnet and Base. The requested activity screen is at least INR 10,000,000 in the last month. Preserve the exact UTC window, source, scope, coverage, FX rate and its date. A 30-closed-day source observation is not the existing rolling 720-hour check. Partial or stale evidence is unknown, not zero or an automatic pass. Volume is not proof of a scam or a concern vote.

## Implementation plan

1. **Transfer and review the evidence.** Obtain the ZIP privately from the sender, verify its SHA-256 and inspect its README. Restore into a fresh isolated directory using Python 3.11 and the bundled dependencies. Review the exact six identities, evidence, report content, provenance, uncertainty, permissions, redistribution and retention before selecting material for deployment. Inspect generated HTML and JSON, not only hashes. Make any revisions as new immutable report versions. Historical YFI and FET incident supplements were prepared separately and are **not** in this ZIP; obtain and review them separately if needed. YFI was a market asset in a reported historical incident, not thereby proof of project misconduct; FET accounts are disputed. The 2026 model history does not backtest the 2023 YFI incident.
2. **Backend contract and migration.** Decide how to add a versioned reference association and import format to production main. Provide validated identity- and hash-bound ingestion, transactional or recoverable idempotence, safe conflicts, backups, and a migration/rollback. Integrate with the existing startup seed machinery deliberately or provide a reviewed migration tool. Maintain pending/synthetic provenance; do not create decisions or approvals. Define server-owned UTC freshness and do not expose stale amounts as live metrics. Review existing PRs and prototype commits before choosing implementation.
3. **Authorization and asset serving.** Design admin-scoped draft reads and a separate approved public report path. Preserve World ID and report-release policy; do not deploy an unauthenticated loopback preview or use synthetic authorization in production. Serve immutable schema-validated report and evidence assets with exact identity, hashes, access control, safe content types and path containment. Do not serve captured third-party HTML as active executable page content. Check retention and third-party data rules, particularly source material that may contain Reddit links.
4. **Frontend reader and case journey.** Port the reusable preview components onto the production web app, using the real authenticated API and case/report identifiers. Preserve current design, case rationale and actionability, readable TL;DR bullets for each of five pillars, evidence links, meaningful graphs where supported, empty/gap/error states, mobile accessibility and chart units. Clearly label historical data and uncalibrated VAE output; do not surface the raw legacy 'maximum loss' or 'Low' as a reliable claim. Link from case to its actual reference report and separate admin actions from consumer experience.
5. **Deployment.** Verify actual Render service revision, persistent storage, worker configuration and environment, and actual Vercel project/revision and trusted origin. Configure the documented seed inputs, storage and CORS only after choosing the integration; a PDF browser or same-volume rendering worker is needed only if generating those assets. Explicitly set `SCOOBY_SCOUT_ENABLED=false`, `SCOOBY_CASE_SYNC_ENABLED=false`, `SCOOBY_MODEL_CALL_BUDGET=0`, `SCOOBY_CASE_MODEL_MAX_CALLS=0`, `SCOOBY_PUBLISH_ENABLED=false`, and `SCOOBY_DEMO_AUTOPUBLISH=false`. Retain `SCOOBY_REPORT_RELEASE=approved` and the existing report access policy; set `SCOOBY_WEB_ORIGIN` to the exact trusted origin. These flags do not prove a generic worker cannot consume existing queued research jobs. For strict display-only operation prefer verified pre-rendered assets and no generic worker, or implement and test a render-only queue and manually triggered route controls. Inspect existing queues before startup. GitHub access alone does not establish Render access or effective deployed environment. Run a staging restore and end-to-end smoke before coordinating production rollout.

Future work, not required for the display-only milestone: wire identity-bound daily history collection and model execution into the worker. A precomputed VAE does not prove that new cases automatically run it. Validate reconstruction hashes, simple-return units, missing dates, sample assumptions and the interpretation of expected shortfall and minimum return. Test out-of-sample behavior before claiming calibration. If GPT-6.1 Terra synthesis is enabled later, independently review its claims; schema/citation validation alone cannot establish entailment.

## Acceptance and checks

- A clean staging restore and repeat restore preserve exactly the selected case/report associations and all bundle digests; existing data survives and a failed import does not leave misleading partial records. Demonstrate rollback and an upgrade test against an existing nonempty database.
- Admin sees pending historical references only with real authorized access; consumers see only genuinely approved releases. Both World checkpoints retain their distinct purpose and leave durable auditable state. No invented actor, approval, gate result or current token claim.
- Case card opens the matching report. Each pillar displays sourced facts, TL;DR, context, timestamps and gaps; supported charts match raw data. Validate six identities, desk/mobile rendering, keyboard accessibility, unavailable states, bad hashes and authorization failures.
- Verify VaR units, confidence and horizon against saved evidence and independently recompute results; label historical, in-sample and uncalibrated. Never present a retrospective 2023 incident as a model backtest when the history starts in 2026.
- Demonstrate the staging and deployed review journey from the seeded data with **zero live agent, model or provider requests**, and confirm disabled worker budgets/configuration. A rendering worker may process already-seeded assets without initiating research.
- Confirm the minimum-activity screen on appropriate source windows, FX and incomplete cases, and ensure no volume result creates a suspiciousness vote. Test expiry on server time including boundary equality, stale persisted reads and source integrity failures.
- Record tested SHAs, deployment config names (never secrets), commands, results, known limits and owner/handoff in the README or deployment notes. Preview and source access must be reproducible on another machine.
