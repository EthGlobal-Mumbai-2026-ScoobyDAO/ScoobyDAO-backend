# 30-day activity prefilter — proposed sidecar

This is an offline evaluator and versioned proposal, not a running collector or an adopted report schema. `activity_30d.evaluate(candidate_id, pool_id, pools_capture, ohlcv_capture, fx_capture, as_of)` consumes three trusted captured byte strings plus exact URL, fetch time and SHA-256. The backend must own acquisition, authoritative time, identity, request budgets, provenance persistence, expiry, the scheduler and the UI integration. Never accept a client-supplied result as verified. Source hashes prove byte integrity, not that the provider is correct. No source requests are performed by this module.

The contract is [activity-30d.schema.json](activity-30d.schema.json), profile `scooby.activity-30d/1-proposal`; [synthetic example](fixtures/activity-30d-synthetic.json) is not real token activity. `pass` means selected-pool volume reaches INR 10,000,000; `excluded` means only that pool's captured volume is below the threshold. `unknown` includes source, identity, integrity, unit, freshness, 720-hour completeness and FX failures. Coverage gives observed/expected hours; no 24-hour extrapolation. A provider-reported explicit zero bucket counts as data; an absent bucket is never filled. Window is exactly 720 closed hourly intervals ending on the last UTC hour boundary, so it lags actual time by under an hour. Duplicate buckets fail closed. Pools, OHLCV and FX captures must each be at most one hour old relative to trusted evaluation time.

Candidate and pool identities must match the unique provider pool relationship and OHLC token-side metadata. Only one specified pool is evaluated; no summing pools, duplicate-pool counting, token-global, CEX or cross-chain coverage is implied. Results may include provider-reported pool reserve in USD and annualized hourly log-return sample volatility (719 returns, square root of 8760), when complete valid prices exist. These are context, not additional thresholds, no guarantee of executable depth, and not legacy VAE metrics. Wash trading and unreliable provider prices/coverage can distort volume and volatility.

## Intended sources and limits

1. Pool identity: GeckoTerminal Public API token-pool page 1. Do not claim that one page lists all venues. The pool must be explicitly identified and unique in the returned page.
2. Pool hourly history: CoinGecko Pro `/api/v3/onchain/networks/{network}/pools/{pool}/ohlcv/hour?aggregate=1&limit=1000&currency=usd&token={base|quote}&include_empty_intervals=false`. [Official REST documentation](https://docs.coingecko.com/reference/pool-ohlcv-contract-address) describes the OHLCV tuple, USD option, max 1000 rows and no-swap gaps. [CoinGecko's on-chain OHLCV documentation](https://docs.coingecko.com/websocket/wssonchainohlcv) explicitly labels volume USD for its websocket. Confirm the precise REST volume-unit semantics and entitlement before enabling live acquisition. One 1000-row response is sufficient only if it actually contains the required 720 distinct hours; truncated, sparse, duplicate and ambiguous data are unknown. No pagination or fills are attempted. Pro endpoint requires configured credentials and plan; they must stay out of URL, output, logs and fixtures.
3. FX: `https://api.frankfurter.dev/v2/providers/ecb/rate/usd/inr`, the named ECB provider, not Frankfurter's default blended rates. The [provider documentation](https://frankfurter.dev/) describes the named-source endpoints and date fields. A bounded unauthenticated read returned HTTP 200 on 6 November UTC; it was a connectivity check and is not persisted as a qualifying capture. Rate must be INR per USD, positive, finite, dated before the evaluation-end UTC date (date-only source cannot establish same-day publication time) and no more than four calendar days old; capture time must be fresh. This intentionally conservative four-day bound is provisional and permits typical weekends, not a universal holiday calendar.

The evaluator converts the **entire captured USD volume using one dated reference rate**, not each trade or each hour at its contemporaneous FX rate. Threshold comparison uses decimal arithmetic. A market-wide INR transaction total, official Indian settlement rate and real-time trade conversion are not claimed. RBI states FBIL has computed USD/INR reference rates since July 2018; do not label the ECB-derived rate an RBI/FBIL rate. [RBI source](https://www.rbi.org.in/Scripts/BS_PressReleaseDisplay.aspx?prid=44393).

## Acquisition and rollout prerequisites

Plan one pool-list request, one OHLCV request per candidate/pool and one cached shared FX request per permitted freshness window; all require durable pre-send provider/cycle reservations and 429 cooldowns. This branch does not implement those calls or set a source budget. Backend must verify CoinGecko Pro access, REST volume units and coverage, fetch and store immutable bytes plus request metadata, avoid duplicate in-flight requests, and prevent stale/future/time-shifted or unauthenticated source data being promoted. Provider failure, unavailable API keys, unsupported pools, partial history, data gaps and FX holidays beyond the freshness policy must remain unknown and visible. No historical candidate should inherit a current capture.

The prefilter is not a concern-group vote, suspicion verdict, automatic investigation, World ID confirmation or report sign-off. Keep the four-independent-verified-concern gate and authenticated human route unchanged; integrate via a separate versioned optional sidecar after backend/frontend agreement. Historical examples may be displayed with unknown activity and explicit historical labels.
