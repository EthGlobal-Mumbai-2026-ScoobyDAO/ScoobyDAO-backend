# Architecture and state contracts

Huey SQLite queue wakes a worker; a second SQLite database is authoritative for candidate, selection, investigation, pillar, job, review and report state. Messages contain no credentials or reports: wake messages carry no payload; durable jobs carry kind, stable ID and reference. Render jobs reference report ID/version/digest. A worker claims one queued job in a SQLite immediate transaction, sets a five-minute lease, and retries failures three times with bounded exponential delay. Periodic reconciliation requeues expired leases. One worker is the supported configuration. Huey was chosen for a small local process and SQLite storage; its queue is not an exactly-once broker. [Huey documentation](https://huey.readthedocs.io/) and [FastAPI tutorial](https://fastapi.tiangolo.com/tutorial/) describe the components.

Transitions: candidate imported -> monitored/unknown -> local diagnostic selection or defer. Normal qualified selection is disabled until real verified concern groups exist. Selection -> queued investigation -> five unavailable pillar records -> incomplete; cancellation and resumption are local state operations. Scan -> queued/running/done with unknown coverage. Report import -> immutable (report ID, version, exact byte SHA-256) -> review request/approve/revise/reject receipt -> HTML job. Local draft rendering is permitted before review and always labeled pending. Approved export is not implemented. No version inherits another version's approval. Receipts are unauthenticated local records and do not demonstrate a human identity.

A worker may lose or duplicate wakeups. Database claiming limits duplicate logical job transitions, but a lease can expire while a worker is still alive; there is no fencing, and this design is not exactly-once for external work. Cancellation is effective before claim; there is no cooperative interrupt of an in-flight process. Model, source, budget and actor interfaces must be developed before live use. External source instructions are data, not actions. No source or model can authorize selection or report review.

The frontend adapter performs frozen JSON Schema, reference, asset path and hash checks before copying a bundle and building the reading surface. Each import is snapshotted and the adapter validates that snapshot; report bytes and digest are then held under a content-addressed path. This local trusted-operator import is not a hardened file upload boundary. A configured headless browser prints the reader to a draft PDF, with digest in its banner and manifest; collapsed details and full-report coverage need further work. The opt-in provider task uses Chat Completions, strict JSON schema and evidence-ID checks, never passes tool definitions, and reserves a call against a persistent default-zero attempt budget. It does not enforce token/rate spending or establish source truth. [Terra model documentation](https://developers.openai.com/api/docs/models/gpt-6.1-terra) specifies Chat Completions and that tool calling requires Responses; [Chat Completions reference](https://developers.openai.com/api/reference/resources/chat/subresources/completions/methods/create) documents structured response format.
